# 结论（先看）

**扣费应改在「话题结束」时执行，而不是「新建会话 / 首条消息」。**

产品语义是「一次需求分析咨询」对应一次费用；现网话题生命周期已有明确终点 `is_topic_closed`（助手回答首行 `结束状态 True`）。按次计费应对齐该终点，而不是对齐会话行创建。

# 现状与问题

## 现网实现

| 步骤 | 行为 |
|:---|:---|
| 创建 dify 会话 | `create_session` → `ensure_dify_session_fee` → S2S deduct |
| 发消息（补丁） | 若 `fee_charged=false`，同步/流式/WS 发消息前再扣一次 |
| 话题结束 | 仅置 `is_topic_closed=true`，与扣费无关 |
| Web「新会话」 | 始终调创建（为修「空草稿不扣费」） |

## 暴露的问题

1. **计费对象错位**  
   用户点「新会话」、试一句、误开空会话，都会扣费；真正「咨询完成」却不作为计费事件。文案写「每次会话咨询」，业务上更接近「每次完成的话题」，不是「每条会话 DB 行」。

2. **空会话 / 未完成话题被收费**  
   用户可能点开就走、换场景、关掉页；若已扣费则白扣。若未结束话题不扣，才符合「咨询结果」付费。

3. **与话题模型不一致**  
   系统已有：进行中（可继续发）→ 结束归档（`is_topic_closed`）→ 可「继续对话」`resume_topic`。扣费挂在创建，与收件箱「已归档话题」、游客「按归档次数」配额逻辑都不对齐。

4. **前一轮补丁治标不治本**  
   「新会话无流水」根因是前端复用空草稿未调创建。在「创建即扣」前提下，强制每次创建会放大误扣；应改时机，而不是把创建与扣费绑死。

# 推荐方案：话题结束扣费

## 计费事件

**唯一扣费触发**：dify 会话由未结束变为结束时（`topic_finished` → `is_topic_closed=true`），且 `fee_charged=false`。

落点：`send_user_and_bot` / `stream_user_and_bot`（及 WS 同源路径）在判定 `topic_finished` 并写库成功后调用 `ensure_dify_session_fee`（或改名为 `charge_dify_topic_fee`）。

## 余额门槛（必要配套）

结束才扣会带来「聊完才发现没钱」。须加**前置校验、不预扣**：

| 时机 | 行为 |
|:---|:---|
| 新建会话 | **不扣费**；可选：余额 &lt; 费率时提示但仍允许创建空会话，或直接拒绝（建议：拒绝新建，避免无效会话堆积） |
| 每条用户消息发送前（未扣费会话） | 校验余额 ≥ 当前解析费率；不足则拒绝发送并引导 `/wallet` |
| 话题刚结束 | 执行 S2S deduct；成功 → `fee_charged=true` |
| 结束扣费失败 | 见下节 |

金额仍用 `resolve_session_fee`；`ref_id=or_session_{id}`；`product=or`，`biz_type=consume_session`；游客 / 人工客服仍不扣。

## 结束扣费失败

话题已根据模型标记结束，但 S2S 失败时建议：

1. **仍写入** `is_topic_closed=true`（咨询结果不应因支付通道抖动回滚）。
2. 保持 `fee_charged=false`；记录错误日志；用户端提示「话题已结束，扣费失败，请充值后重试」。
3. 提供补扣入口：打开已结束未扣费会话、或定时/手动「确认扣费」；余额充足后补扣成功再标 `fee_charged`。
4. 未扣费的已结束话题：**禁止** `resume_topic` 继续对话，直至补扣成功（避免白嫖多轮）。

## 「继续对话」

`resume_topic` 把 `is_topic_closed` 改回 false，开启新一轮咨询。建议：

- 恢复时**不立刻扣费**；
- 该会话若上次已 `fee_charged=true`，恢复后将 `fee_charged` 重置为 false（或引入 `fee_charge_epoch` / 按「话题轮次」计费），使**下一次再结束**再扣一笔；
- `ref_id` 若仍用 `or_session_{id}` 会与 manager 幂等冲突，须改为 `or_session_{id}_topic_{n}` 或带时间戳/轮次。

（若首期不做 resume 再计费，须在需求里写死：继续对话免费 / 暂不支持，避免歧义。）

## 长期未结束的会话

不自动扣费。运营若担心「开着不结」：

- 首期可接受（未交付咨询结果不收费）；
- 后续可加「超时未活跃自动结束并扣费」或「手动结束话题」，**不在本次必做**。

## Web「新会话」按钮

与扣费解耦后：

- **允许**复用同智能体空草稿（减少无意义会话行）；
- 或继续「始终创建」仅影响列表体验，**不再触发扣费**。
- 推荐恢复「空草稿复用」，降低垃圾会话。

# 与现行文档的冲突

| 文档 | 现行表述 | 应改为 |

| `02-dr/…实施方案` / 资金设计 | create + 首条消息补扣 | 话题结束扣费 + 发送前余额校验 |
| QA「新会话无流水」 | 按创建触发理解问题 | 根因仍成立，但正确产品行为不是「点新会话就该有流水」 |

# 迁移与存量

| 存量 | 处理 |
|:---|:---|
| 已 `fee_charged=true` 且未结束 | 已预扣：话题结束时跳过（幂等） |
| 已结束且 `fee_charged=false` | 打开或后台任务补扣；或一次性脚本按结束时间补 |
| 探测扣费产生的流水 | 保持不动，属运维探测 |

上线顺序建议：先改扣费时机与余额校验 → 再决定是否回退「新会话强制创建」→ 再处理 resume 轮次与 `ref_id`。

# 明确不做（本方案边界）

- 不按 token / 消息条数计费（仍为固定「每次话题」价）
- 不在 mgr 建第二套费率
- 人工客服不计本费种
- 首期可不做「超时自动结束扣费」
