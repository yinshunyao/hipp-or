# 功能设计

## 管理后台（hipp-admin）：菜单失败与无权限说明

- **接口**：动态菜单仍通过 `GET /auth/getMenuList`（与现有 axios 封装一致）；若响应未按约定返回成功业务数据（拦截器未向调用方返回有效 `data`），视为「菜单加载失败」。
- **路由**：新增常量路由 `/no-access`（无 Layout 侧栏依赖），展示说明文案与主按钮「退出并更换账号」（调用既有 `auth` store 的 `logout`，回到登录页）。
- **统一加载**：抽取 `loadDynamicMenuRoutes`（内部 `generateRoutes` + `addRoute` + `setIsAddRouters`），**登录成功后的首次菜单加载**与 **`permission.ts` 路由守卫**共用，避免两套逻辑不一致。
- **失败时导航**：菜单加载失败时跳转 `/no-access`，不再依赖用户停留在无顶栏的 404。
- **404 页**：当存在登录 token 时额外展示「退出系统」，便于在异常页直接换账号。

## 小程序登录入口

- 登录页**默认**为「手机号 + 短信验证码」：`获取验证码`、验证码输入、登录提交。
- 提供切换到「账号密码登录」的入口（与默认态二选一展示，具体交互由前端实现）。
- **不再提供**「微信授权登录」入口；`hipp-uni` 登录页移除微信登录按钮及相关弹层。
- 账号密码分支：输入框字段名沿用 `telephone`（兼容历史客户端），语义为「手机号或账号」；密码默认掩码，支持显隐切换（仅前端展示态切换，不改变值）。

## 账号密码登录（`POST /auth/login`，`method=0`）

- 请求保持现有结构：`telephone` + `password` + `method=0` + `platform=1`。
- 登录标识解析规则保持现有实现：
  - 合法手机号：按 `telephone` 精确匹配；
  - 含字母账号：先 `name` 精确匹配，再 `nickname` 精确匹配。
- 失败文案继续使用统一口径：
  - 账号不存在/密码错误：`账号或密码错误`；
  - 冻结：`此账号已被冻结`；
  - 无权限：`此账号无权限`。

## 短信验证码登录（`POST /auth/login`，`method=1`，`platform=1`）

- 请求字段沿用现有约定：`telephone` 为手机号；`password` 字段承载**短信验证码**（与历史接口一致）。
- 发送验证码：登录场景（小程序与管理后台短信登录）统一调用 **`POST /auth/sms/send`**，请求体 JSON：`{ "telephone": "<11位手机号>" }`；不要求手机号已注册；底层仍用 `utils/sms/code.CodeSMS`（Redis 存码、频控等）。**禁止**将登录发码指向 `POST /vadmin/system/sms/send`（该路由为历史实现：`telephone` 走 query，且要求库中已存在该手机号，易与小程序自助注册发码混淆）。
- **处理顺序调整（相对原「先查用户再验码」）**：对 `platform=1` 且 `method=1`，应先校验短信验证码正确且未过期；校验通过后再按手机号查询用户。
  - **已存在用户**：继续走与现有一致的登录校验（拉黑、冻结、`is_staff` 等），通过后颁发 token。
  - **不存在用户**：**自动创建用户**后颁发 token（仅当验证码校验已通过）。新建用户默认建议：
    - `user_type`：使用 `system`（短信自助注册与系统用户同源管理），或与现有枚举一致的独立取值须在实现与迁移说明中统一，**不得**再依赖微信登录写 `wechat`；
    - `telephone`：本次手机号；
    - `name` / `nickname`：按手机号派生默认展示名（如「用户」+ 后 4 位，规则与现网数据风格一致即可）；
    - `is_staff=True`、`is_active=True`；`password`：随机哈希，兼容 token 载荷中的 `password` 校验；
    - `wx_nickname` / `wx_avatar` 可空；不要求绑定 `wx_server_openid`。
- `platform=0`（管理端等）的 `method=1` 行为：若仍需「仅已存在用户可短信登录」，可在服务端按 `platform` 区分：**仅 `platform=1` 启用自动建号**，避免后台账号被误创建（实现时以代码分支为准）。

## 微信授权登录（`/auth/wx/login`）与小程序

- **小程序前端**：不再调用 `/auth/wx/login`。
- **服务端**：接口可暂时保留供旧版客户端或运维排障，但新需求不以微信登录为交付路径；若后续完全下线，另立变更单删除路由与相关校验。

## 用户类型字段（`vadmin_auth_user`）

- 现有字段 `user_type`、`wx_nickname`、`wx_avatar` 继续用于历史数据与展示。
- 通过**短信自动注册**的新用户：`user_type` 建议为 `system`（与「后台或密码创建的用户」同一管理口径）；若历史已有大量 `wechat` 用户，并存期间列表与标签逻辑不变。

## 登录响应扩展

- `/auth/login` 返回体继续包含 `user_type` 等字段，供前端识别。
- 兼容保留：`access_token`、`refresh_token`、`token_type`、`is_reset_password`、`is_wx_server_openid`。
- 配置了 `HIPP_MANAGER_BASE` 时：登录/SSO 须拿到 `manager_token`（拿不到则登录失败），写入响应并由服务端 Redis 缓存（键 `or:mgr_tok:{user_id}`，TTL 约 12h）。
- **初设密码场景标志（与短信首次注册对齐）**：当用户属于「短信自动建号且尚未在系统内完成自选密码设置」时，登录响应或当前用户信息接口中须向小程序暴露**只读布尔**（命名建议 `must_set_password_without_old` 或与之一致），用于前端在「修改密码」页**隐藏「当前密码」**并跳过前端校验；非该场景为 `false`。具体字段落位（登录 JSON / `GET /auth/user/current` 等）以实现为准，须与 `hipp-uni` store 同步约定。

## 在线权威（hipp-manager）

- 本地 JWT 仍负责绑定用户与 RBAC；**是否在线**以 manager 会话为准。
- `AllUserAuth` / `FullAdminAuth` 及 `mp_chat` WebSocket 鉴权：本地 JWT 通过后，非 `mp_guest` 用户须用缓存的 `manager_token` 调 manager `GET /api/auth/me`（按 token hash 短缓存约 30s；失败约 5s）。失败则 401 并清除缓存令牌。
- `user_type=wechat` 且从未缓存过 manager 令牌：跳过二次校验（纯微信会话）。`mp_guest` 跳过。
- 前端只带产品 `Authorization`，不单独申请在线状态。

## 初设密码与重置当前密码（小程序短信首次注册用户）

- **问题**：`platform=1` 短信自动建号用户入库时使用**随机密码**（用户不可知）；若仍强制「当前密码」则无法完成首次改密。
- **判定**：使用专用标志区分「从未设置过自选密码的短信注册用户」与「后台初始化/重置临时密码后须改密」（后者用户已知短信/邮件中的临时密码，**仍须**填当前密码）。建议在 `vadmin_auth_user` 增加布尔字段（如 `must_set_password_without_old`，默认 `false`）：仅在 `create_user_for_mp_sms_register` 创建用户时置为 `true`；用户**首次**成功设置新密码后置为 `false`。后台批量初始化密码、管理员改密等路径不得误将该标志置为 `true`。
- **兼容迁移前短信自助用户**：库中 `must_set_password_without_old` 可能为 `false`，但业务上仍属「无旧密码可填」。服务端在登录响应、`GET /user/admin/current/info`、`POST .../reset/password` 等处使用统一函数 `user_must_set_password_without_old`：在标志为真 **或**（`is_system_created=false` 且 `is_reset_password=false` 且 `user_type≠wechat`）时视为须无旧密码设密；微信来源用户排除。
- **接口**：`POST /vadmin/auth/user/current/reset/password`（或项目实际路径，与现有 `ResetPwd` 一致）在 `must_set_password_without_old==true` 时：`old_password` 允许为空或省略，**跳过**与库内哈希比对；仅执行新密码复杂度与 `password_two` 一致性校验；成功后写入新哈希、`is_reset_password=True`、`must_set_password_without_old=False`。当 `must_set_password_without_old==false` 时，行为与现网一致：`old_password` 必填且须通过 `reset_current_password` 校验。
- **小程序**：`subpkg/mine/pwd/index` 根据 store 或用户信息中的上述标志，为 true 时**不展示**「当前密码」表单项且不校验该项；导航标题可为「设置密码」或沿用「修改密码」由产品统一，须在 `doc/02-dr/04 小程序对话/小程序导航与我的页设计.md` 与测试设计中保持一致。

# 数据模型

- 表：`vadmin_auth_user`
- 新增字段：
  - `user_type` `String(16)` 非空，默认 `system`；
  - `wx_nickname` `String(128)` 可空；
  - `wx_avatar` `String(500)` 可空。
- **初设密码标志（待实现本需求时补充迁移）**：`must_set_password_without_old`（命名以迁移脚本为准）`Boolean` 非空默认 `false`；短信自动建号创建时置 `true`；首次成功设置自选密码后置 `false`。历史行统一 `false`。
- 迁移方式：通过 Alembic 增量迁移新增字段；历史用户回填 `user_type=system`。

# 约束与边界

- 短信登录依赖阿里云短信（或当前项目已接入的短信通道）与 Redis 验证码存储；通道未配置时须返回明确错误，不得静默失败。
- 自动建号仅发生在 **验证码已验证通过** 之后，避免未验证手机号占用库表。
- 现阶段不引入数据库外键或新关联表；用户类型信息直接存储在用户表字段中。
- 用户类型仅用于来源区分与业务判定，不影响现有角色权限模型。
- 员工用户（非超级管理员）在**未关联任何角色**时，`FullAdminAuth` 路径下计算数据权限范围时按 **data_range=0（仅本人）** 处理，避免对空角色列表取 `max` 导致接口异常；`GET /vadmin/auth/user/admin/current/info` 等依赖该逻辑的接口应正常返回。

## 启动初始化补充（`hipp-api/run.sh`）

- 启动前继续通过核心表存在性检查决定是否执行 `init`。
- 当目标数据库连接返回 MySQL `1049 (Unknown database)` 时，脚本应自动执行建库：
  - 使用相同主机、端口、用户名、密码建立不指定库名的连接；
  - 执行 `CREATE DATABASE IF NOT EXISTS <db_name> CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci`。
- 建库成功后重连目标库并恢复原流程：
  - 核心表存在：直接启动服务；
  - 核心表缺失：执行迁移和种子初始化后启动服务。
- 仅数据库不存在场景启用自动建库；权限不足、网络不可达、认证失败等异常仍保持失败退出。
- 内嵌 Python 校验（数据库 URL、核心表检查）必须以 **`run.sh` 所在目录** 为项目根加入 `sys.path` / `PYTHONPATH`，子进程显式传入与脚本一致的 `HIPP_RUN_ROOT`，避免仅拷贝 `run.sh` 或错误环境变量导致无法导入 `application.database_url`；导入失败与「未配置连接串」须在日志上区分。

# 前端（hipp-uni）

- 登录页默认区：手机号、验证码、`获取验证码`（倒计时防刷）、登录按钮；错误与发送结果 Toast/文案与后端一致。
- 提供切换到账号密码登录；密码框显隐切换行为不变。
- 移除微信登录按钮、`getPhoneNumber` 登录链路、与微信一键登录相关的弹层与接口调用。
- **用户协议 / 隐私政策**：点击《用户协议》《隐私协议》**不**使用 `subpkg/common/webview` 或配置中的远程 URL；正文以 `hipp-uni/common/legal/static-texts.js` 内置字符串为准，须与 `hipp-or/doc/99-ops/luo/用户协议.txt`、`隐私政策.txt` 保持一致（更新政策时同步修改上述三处）。交互为**全屏遮罩 + 居中面板**：`scroll-view` 展示正文；若正文高度大于滚动区高度，用户需触发滚动至底部（`scrolltolower`）后，底部「我已阅读并返回」按钮才可点；若正文未超出滚动区，打开弹窗时即允许点击确认。首次确认后，客户端将该项「已读确认」写入本地存储（`hipp-uni/common/legal/consent-storage.js` 约定 key）；**再次打开同一协议**时底部按钮为「返回」，无需重新滚底。当**两项协议均已确认**（含历史会话已写入存储）时，自动勾选「阅读并同意」；用户若在该状态下手动取消勾选，本页会话内不再自动勾选，直至其再次在弹窗内完成一次非「仅返回」的确认且两项仍均满足。
- 登录成功后仍持久化 `token`、`refreshToken`、`userType` 等，与现有请求拦截器一致。
