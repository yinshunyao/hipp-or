# 背景

1. 用户在需求咨询、商业评估对话中，除文字外常需补充语音说明、现场照片、需求文档或截图；当前 hipp-or（Web / 小程序）与 Dify 转发链路均为纯文本，无法上传附件，也无法语音输入。
2. 产品侧希望附件主存储落在平台公共媒体服务（hipp-manager `data/media/`，对外 `/media/` 绝对 URL），对话历史可回看；向大模型理解时通过 Dify Chat 的 `files` 能力传递，优先使用可公网拉取的 URL（`remote_url`），避免强制再存一份到 Dify 本地。
3. 附件体积与个数须与线上 Dify 应用限制对齐，并满足业务「单次发送附件总体积小于 20MB」；语音输入优先转为文字再进入现有对话链路，降低对多模态音频理解的依赖。
4. 本需求覆盖 `hipp-api` 对话模块、`hipp-web`、`hipp-uni`，以及生产 Dify 应用「需求分析」「商业评估」的能力开关与限额；密钥仍不得下发客户端。

# 目标

1. 允许已登录用户在智能体会话中发送图片与常见文档类附件，并在历史消息中回看。
2. 将附件经平台媒体服务落盘并取得绝对 URL 后，由服务端按 Dify 约定把文件（优先 `remote_url`）随本轮 `query` 一并转发，使模型能结合附件作答。
3. 提供语音输入：录音后转写为文本，填入或直接作为本轮用户文本发送（转写失败可提示重试）。
4. 在客户端与服务端强制校验：单次消息附件总体积小于 20MB，且单文件/类型上限不松于对应 Dify 应用配置。

# 要求

## 功能性要求

- **范围**：仅 `session_kind=dify` 的智能体会话支持附件与语音转写后发送；人工客服会话本版不做附件（保持纯文本，除非后续单独需求）。
- **附件类型（首期）**：图片（至少 JPG/JPEG/PNG/GIF/WEBP）；文档（至少 PDF、TXT、MD、DOC/DOCX、XLS/XLSX、CSV）。视频本版不做。
- **存储**：附件上传经 `hipp-api` 门面校验后，写入 **hipp-manager** 公共媒体（本地盘 + `/media/`）；消息侧持久化附件元数据（类型、文件名、大小、MIME、绝对 URL 等），供历史与分享页展示。禁止对话附件再直连本产品内阿里云 OSS 占位配置。
- **Dify 传递**：调用 `POST .../v1/chat-messages` 时携带 `files[]`；传递方式优先 `transfer_method=remote_url` + 媒体绝对 `url`；须保证 Dify 服务端能 HTTP GET 到该 URL。若联调确认不可达，允许降级为服务端代传 `local_file`（`/files/upload`），仍以平台媒体为业务主存。
- **大小与个数**：单次发送附件**总体积 &lt; 20MB**；单文件大小、单次个数、扩展名白名单须与已发布的 Dify 应用 `file_upload` / `fileUploadConfig` **取更严一侧**对齐；配置变更时须同步改客户端提示与后端校验常量（或可配置项）。
- **纯附件消息**：允许附件存在且用户文本为空时发送（此时 `query` 可用约定占位短句，如「请结合附件」），具体以设计为准，但不得再强制 `query` 非空阻断附件轮。
- **语音**：提供录音入口；转写为文本后进入现有发送路径。转写可走 Dify `/audio-to-text` 或平台已接入的同级能力；本版不要求把原始音频作为 `files[].type=audio` 交给多模态理解（可作为后续增强）。
- **客户端**：`hipp-web` 与 `hipp-uni` 输入区支持选图/选文件、预览与删除待发附件、发送前体积校验；气泡可展示图片缩略图与文件名下载/打开（权限允许范围内）；列表 `last_message_preview` 对附件轮有可读摘要（如 `[图片]`、`[文件] xxx.pdf`）。
- **Web 快捷入附**：`hipp-web` 对话输入区支持将模型白名单内的图片/文件**粘贴**（含截图）或**拖拽**进入输入区，与点选附件共用同一上传与待发校验；人工客服会话不适用。
- **密钥与直连**：禁止客户端持有 Dify `app_key` / `api_server`；上传与转发一律经 `hipp-api`。
- **Dify 应用运营**：须开启文件上传（含 `remote_url`）、按类型扩展白名单；图片相关 LLM 节点开启 vision；语音转写若用 Dify STT 则开启 speech_to_text；「需求分析」「商业评估」两应用限额与行为一致落地。
- **待发取消删盘**：用户从待发列表移除已上传附件时，须调用服务端删除，清除平台媒体文件；仅前端去掉预览不算完成。
- **话题结束清理**：**不得**删除已写入消息 `attachments` 的媒体（历史/分享页须可继续打开原图）。待发取消仍删盘；全站孤儿 GC 仅清理从未被任何消息引用的落盘文件。清理失败不影响结题与扣费主路径。
- **全站孤儿定时清理**：每日约 **凌晨 3 点**（`Asia/Shanghai`）扫描平台 `or/.../chat/` 媒体；删除「超过宽限期（默认 24h）且未出现在任意消息 `attachments`、也未出现在任意助手正文 `/media/` URL 中」的文件（含上传后未发送即离开的孤儿）。须 Redis 分布式锁，避免多进程重复扫；失败只记日志。

## 非功能性要求

- 上传失败、Dify 拒收附件、媒体 URL 不可达时，返回明确错误文案；已写入的用户消息策略以实现设计为准（避免半截不可追溯状态）。
- 不改变现有流式主路径（WS / SSE）与话题结束「结束状态」过滤语义。
- 不引入数据库级外键；附件与消息的关联在应用层维护。

## 明确不做（本版）

- 视频附件；人工客服附件；客户端直连 Dify；仅把 URL 写进 `query` 文本而不走 `files[]` 作为正式方案。

## 需求

1. 多模态附件与语音输入：`POST /mp/chat/upload`、`audio-to-text`、发送三路径带 `files`（媒体 URL + Dify `remote_url`）、消息 `attachments` 落库；Web / 小程序输入区附件与语音转写；Web 粘贴/拖拽入附；Dify 导出开启 file_upload / vision / STT。见设计与实施方案。
2. 对话附件存储前移 hipp-manager 公共媒体（本地盘 + `/media/` 绝对 URL），or 门面转发；不再直连本产品 OSS 占位配置。
3. 待发取消删盘（`DELETE /mp/chat/upload`）；话题结束**保留**消息 `attachments` 媒体（不再因未写入助手正文而删盘）；孤儿靠全站 GC。
4. 全站孤儿媒体定时 GC：每日约 03:00（Asia/Shanghai）+ 宽限期 24h；manager `POST /api/s2s/media/gc`。
